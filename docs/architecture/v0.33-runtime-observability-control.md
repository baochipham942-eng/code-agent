# v0.33 运行时可观测与控制架构

本文描述 Agent Neo v0.33.0 新增和收口的运行时主链：模型能力如何进入请求，计划与工具如何过控制门，执行事实如何写入 trace，以及检查器、语音审计和产物工作台如何消费这些事实。

发布事实与产品边界见 [v0.33.0 as-built spec](../plans/2026-08-19-neo-v0.33-as-built-spec.md)。本文不替代 `agent-core.md`、`tool-system.md`、`dynamic-workflow.md` 和 `live-voice.md` 的模块级说明。

## 1. 主链

```text
ConversationEnvelope
  ├─ provider + model + searchEnabled
  └─ text / voice / plan intent
            │
            ▼
ContextAssembly + modelCapabilityMatrix
  ├─ protocol: chat-completions | responses | anthropic-messages
  ├─ built-in search / external search
  └─ thinking + request compatibility
            │
            ▼
AgentLoop / messageProcessor
  ├─ normal response
  ├─ pending plan approval ───────► PlanApprovalCard ─► approved meta turn
  └─ tool calls
            │
            ▼
ToolExecutionEngine
  ├─ native / deferred / PTC nested calls
  ├─ capability broker + compensation registration
  └─ ToolExecutor
       ├─ schema / policy / path / write isolation
       ├─ permission classification + approval source
       └─ handler execution
            │
            ├──────────────► tool execution ledger
            └──────────────► TurnTraceRecorder
                               ├─ 8 events / 2 s incremental append
                               ├─ terminal flush
                               └─ capability / compensation events
                                            │
                    ┌───────────────────────┼──────────────────────┐
                    ▼                       ▼                      ▼
             Session Inspector       Voice Audit            Turn / Artifact UI
             two-level view          timeline               outcome + follow
```

## 2. 状态所有权

| 状态 | 唯一 owner | 消费者 | 持久化语义 |
|---|---|---|---|
| 模型能力 | `modelCapabilityMatrix` | request builder、ModelRouter、设置与诊断 | 代码声明；未声明即保守默认 |
| 逐轮联网意图 | `ConversationEnvelope.searchEnabled` | provider adapter、外部搜索工具 | 随消息事实；不从 UI 全局状态反推 |
| 计划审批 | `PlanApprovalRecord` | PlanApprovalCard、TaskManager、下一 meta turn | pending / approved / revision_requested 终态不可重复决策 |
| 权限决策 | ToolExecutor + permission handler | handler、ledger、模型错误文本、审计 UI | 来源由处理器自报；append-only 决策记录 |
| 工具执行 | ToolExecutor / ToolExecutionEngine | UI、TaskManager、artifact follow | begin / complete 成对；未闭合 begin 是崩溃证据 |
| 轮内 trace | `TurnTraceRecorder` | Session Inspector、结果印章、诊断 API | JSONL 增量 append；允许崩溃前缀 |
| 能力装卸 | `CapabilityUnitRuntime` | skill surface、trace | depends/provides 图 + LIFO inverse |
| 产物跟随 | renderer `artifactFollowStore` | Preview / Workbench | 会话级临时 UI 状态，不是交付验收状态 |
| 语音轮次 | voice session / transport | live status、审计、派活投影 | 用户开口优先；审计事件与普通对话上下文分离 |

## 3. 请求前的能力消费

### 3.1 模型能力矩阵

能力矩阵以 `(provider, modelId)` 为键，输出协议、内置搜索、交错思考、请求兼容字段和 Responses endpoint 位置。合并顺序是保守默认、provider 默认、精确模型声明。

这条边界解决三个同族问题：

- 同名模型在官方 provider 和中转 provider 上可能不是同一协议。
- provider 支持某能力不代表所有历史模型都支持。
- 设置页展示“支持搜索/思考”必须与真实 request builder 使用同一判定结果。

关键文件：

- `src/host/model/modelCapabilityMatrix.ts`
- `src/host/model/providerRuntimeCapabilities.ts`
- `src/host/model/providers/responsesProvider.ts`
- `src/host/model/providers/wrappers/responsesWrapper.ts`

### 3.2 联网双路径

联网有两条受控路径：

1. 模型原生搜索：能力矩阵声明后，由 qwen `enable_search` 或 DeepSeek Responses `web_search` 进入本轮请求。
2. Neo 外部搜索工具：智谱 / MiniMax 凭据由设置读取，经 `ExternalSearchService` 归一结果与失败原因。

两条路径都受逐轮 `searchEnabled` 约束，但错误合同不同：模型原生搜索错误属于 provider response；外部搜索错误属于 tool result。不能把二者合并成一个不可追的“联网失败”。

## 4. 执行控制面

### 4.1 计划审批边界

`exit_plan_mode` 只生成 proposal 与 pending record。`shouldEndRunForPlanApproval()` 结束当前 run，确保批准前没有后续工具动作。批准后：

1. 校验步骤数量、长度和唯一 id。
2. 记录编辑、删除和重排事实。
3. 原子替换 TaskManager 任务。
4. 写回 approval record。
5. 发送不可见于普通历史的 `<approved-plan>` meta turn 启动新 run。

请求修改只发送 `<plan-revision-request>`，明确要求重新提案且禁止执行。

### 4.2 ToolExecutor 单一入口

Native、deferred tool、PTC `tools.X()` 和 agent loop tool call 最终都进入 ToolExecutor。执行顺序保持：

```text
schema normalization
  -> policy / trust / path authority
  -> write isolation
  -> permission classification
  -> approval handler
  -> compensation registration when applicable
  -> handler
  -> normalized result + ledger + trace
```

PTC worker 不直接拥有文件、网络或 shell 权限。nested call 通过 shadow adapter 带回同一 session/run context，避免脚本运行时形成第二权限域。

### 4.3 审批来源

`RequestPermissionResult` 兼容旧 boolean，同时支持结构化来源：

- 批准：`user`、`dev-auto-approve`、`scripted`
- 拒绝：`user`、`no-approval-ui`、`timeout`、`cancelled`、`fail-closed`、`scripted`

裸 boolean 保留旧语义，`false` 等价真人拒绝。新 handler 必须返回结构化结果，尤其不能按调用入口名称猜拒绝来源。分类器错误会写入 decision trace，并继续 fail-closed。

## 5. Trace 与能力生命周期

### 5.1 TurnTraceRecorder

Turn trace 是轮级事实流，包含 request manifest、模型响应、工具、权限、结果、补偿和 capability lifecycle。它有两类 flush：

- 增量 flush：累计 8 条或 2 秒，先到者触发 append。
- 终态 flush：轮次结束、取消或失败时写入剩余事件。

增量 append 的目标是 crash-readable，不承诺崩溃瞬间的内存事件零丢失。Inspector 读取落盘前缀后接 live tail，并按 event identity 去重。

### 5.2 CapabilityUnitRuntime

v0.33 的 exchangeable unit 当前只开放 `skill`，但 capability key 已统一为 `skill|tool|plugin|connector|extension:<id>` 命名空间。加载前验证：

- provides 非空且全局唯一。
- depends 必须由已加载单元或 external keys 满足。
- 依赖图无环。
- 每个 apply 同时登记 inverse。

加载中途失败会逆序 rollback 已成功步骤；卸载时若仍有 dependent 则拒绝。生命周期结果进入 turn trace。

### 5.3 发射类动作补偿

Capability broker 在工具 handler 前为外部或持久化副作用登记 compensation metadata。登记至少包含补偿 id、工具身份、目标摘要和触发时点。此机制提供恢复入口与审计线索；跨服务一致性仍由具体 connector/tool 的业务补偿实现负责。

## 6. UI 投影边界

### 6.1 Session Inspector

Inspector 的两层视图分别回答：

- 这一轮最终发生了什么。
- 每个模型、工具、权限和补偿事件按什么顺序发生。

它只消费 trace API，不读 renderer 临时状态推断执行。历史 trace 缺失时展示证据缺席，不能合成“成功”或“失败”。

### 6.2 Voice Audit

Voice Audit 从会话动作菜单进入，消费语音审计路由和会话事件。打断证据、等待、忽略轮次、审批重连和任务投影保留独立事件类型。审计事件不自动回灌普通对话 history，避免诊断文本污染下一轮判断。

### 6.3 Artifact Follow

`useArtifactFollow` 监听 tool start、artifact write、progress 和 end。自动打开只在当前会话、用户没有操作其他工作台视图、且该会话未暂停跟随时发生。否则仅后台刷新 tab 并给 attention 标记。成功完成后等待 1100ms 收尾刷新；失败立即结束跟随并保留现场。

## 7. 故障策略

| 故障 | 策略 | 用户/审计可见结果 |
|---|---|---|
| 未声明模型能力 | 保守默认 | 不发送未经验证的协议字段 |
| 外部搜索无凭据或限流 | 结构化失败 | 点明来源与失败类别 |
| 无审批 UI | fail-closed | `no-approval-ui`，不冒充用户拒绝 |
| 分类器异常 | fail-closed + trace | `classifier_error/<source>` |
| capability 缺依赖或成环 | 加载前拒绝 | failed lifecycle event |
| capability 中途加载失败 | LIFO rollback | 原错误 + rollback errors |
| trace append 失败 | 执行继续、记录 warn | Inspector 可能只有部分证据 |
| 计划已被决策 | 拒绝重复提交 | `ALREADY_RESOLVED` |
| 用户操作其他工作台视图 | 停止抢焦点 | Preview 后台更新/attention |
| 语音证据不足或分类器故障 | 等待或忽略 | 不抢话、不宣称已执行 |

## 8. 证据与演进边界

- 协议、权限、trace、计划、产物跟随的主要证据是 hermetic/fault-injection 测试。
- 长会话滚动同时有 renderer 测试和 `docs/perf/long-session-gold-latest.json` 的运行证据。
- 真实设备语音、真实外部账号和长时间多任务恢复仍需独立 real-runtime 验收，不能由单测替代。
- `v0.33.0` 之后 #1258、#1259、#1260 的 main 变更不回写成 v0.33 已发布合同；下一版 spec 应在新 tag 基线上吸收。
