## 登记表最终形态

`USER_VISIBLE_SYSTEM_EVENT_REGISTRY`：metadata 键 → `{ presentation, subtype?, attach }`。

| 键 | presentation | subtype | attach |
|---|---|---|---|
| `voiceCallSummary` | `summary` | `voice_call_summary` | `current-turn` |
| `voiceCallFailure` | `error` | `error` | `current-turn` |
| `voiceWorkFailure` | `error` | `error` | `matched-turn` |
| `voiceWorkSettled` | `settle` | —（不成节点） | `matched-turn` |

- `presentation: 'error' | 'info' | 'summary' | 'settle'`：前三种投成节点；`settle` 不成节点，只把结局章盖到按 `workItemId` 对回的派活轮上（对不上就丢弃，沿用 X5.5-A2-a 原语义）。工单要求「每一项都能投出节点」对前三类逐项断言；`voiceWorkSettled` 的设计语义就是不成节点（契约注释明示「这条消息不进对话」），表驱动用例对它断言的是「不成节点 + 章盖对轮」，不改它的行为。
- `attach: 'current-turn' | 'matched-turn'`：四段分支原有的挂轮策略差异收进这一个字段。
- 另有一档 `INTERNAL_SYSTEM_METADATA_KEYS = ['backgroundTaskResult']`：允许出现在 system 消息上但不构成用户可见事件的内部投影键（`sessionCommandCenter.ts` / `voiceTaskResultProjector.ts` 都在写），哨兵对它们静默。通用标注轴 `source` / `correlation` / `voiceTranscript` 不参与登记判定。
- 编译期断言：登记表的键必须存在于 `MessageMetadata`（`UserVisibleSystemEventKey extends keyof MessageMetadata`）。
- 写入侧约束 `SystemEventMessageMetadata` = 登记表键 ∪ 内部档键 ∪ 标注轴；落库 system 消息写别的键 → 编译期报错。

## 表驱动测试的用例生成方式

`tests/renderer/hooks/useTurnProjection.systemEventRegistry.test.ts`：

- `SAMPLE_PAYLOADS` 的类型是 `{ [K in UserVisibleSystemEventKey]: NonNullable<MessageMetadata[K]> }` 全量映射——登记表加一项而测试没补样本，**编译期报错**；键拼错同样报错。
- `for (const [key, spec] of Object.entries(USER_VISIBLE_SYSTEM_EVENT_REGISTRY))` 逐项生成用例：`presentation === 'settle'` 断言「不成节点 + `voiceWorkOutcome` 盖在派活轮上」；其余断言「投出 type=system 节点 + subtype 与表一致 + content/metadata 透传」；`attach === 'matched-turn'` 额外构造「派活轮之后又开一轮」的场景，断言事件挂回派活轮而不是最新轮。
- 另有四条固定用例：裸 `role:'system'` 无 metadata 仍被跳过（底线）、只带 `source` 标注不报错、`backgroundTaskResult` 内部档不报错、未登记键（`voiceFutureEvent`）开发档 `console.error` 一次且仍不投影。

## 守不住的断言（如实记录）

1. **「登记表机制本身被架空」没有可观测失败面**——#908 施工者踩过的形态今天依然成立：把投影层查表那段改成永远不命中（等价于当年的 `if (false)`），裸 system 底线用例照样绿，因为总闸之后的分支都门在 `role === 'user' | 'assistant'` 上，掉下去的 system 消息本来就产不出节点。真正的风险变异是**新增一个放行 system 的渲染分支**，那属于新增代码，只能靠 review 拦。本报告不留一条不可能失败的测试冒充覆盖（沿用 T3 测试文件的既有结论）。
2. **表驱动用例对「摘登记项」自身不转红**——摘掉一项，表驱动循环自动少一条用例，这是表驱动的固有属性。兜这层的是事件级测试（`useTurnProjection.voiceCallFailure.test.ts`）+ 写入侧编译约束，上面变异验证的两路红信号都来自它们。若未来四类事件没有各自的事件级测试，摘项就只剩编译期一路信号（写入点报 TS2353）。
3. **「新事件该用户可见」的意图无法纯机器判定**——有人在 `MessageMetadata` 加新键、落库时绕开 `SystemEventMessageMetadata`（直接标成 `MessageMetadata`）且不登记，编译期拦不住；运行时只剩开发档 `console.error` + 哨兵用例的红。生产档维持现状跳过，这是工单定调，不是缺口。

## 边界说明

- 总闸形态：四段分支合并进单个 `if (msg.role === 'system') { ... continue; }` 块，所有路径（未登记 / settle / 节点类）都以 `continue` 收尾，未匹配的 system 消息跳过行为逐条保留。工单「不许拆总闸」守的是这个行为，未做通用兜底渲染。
- 开发档判定与 `typedInvoke.shouldValidateResponse` 同例（`import.meta.env.DEV`，Node 兜底 `NODE_ENV`）；vitest 下 `DEV=true`，哨兵用例直接走真实代码路径。
- `sessionCommandCenter.ts` 也落 `role:'system'` + `backgroundTaskResult`，不在工单指定的写入侧范围（工单点名 `src/host/services/voice/*`），未加 `satisfies`；它已被 `INTERNAL_SYSTEM_METADATA_KEYS` 覆盖，哨兵不会误报。
- 未做「清理无用分支」类顺手活；四个 voice 分支的语义（含 D5 钉尾、matched-turn 倒查）逐条保留。
