## 1. 孤儿成因结论

真机证据（`system-info.json`）：三代 msedgewebview2 并存，最老孤儿存活 4 天、工作集 600KB 僵尸态；宿主 app 早已退出（含任务管理器强杀场景）。逐条查源码坐实两条独立成因：

1. **WebView2 子孙进程没有任何 OS 级绑定手段兜底**。它们不是本进程 `Command::spawn()` 出来的（是 WebView2 Loader 内部拉起的浏览器/GPU/渲染进程），拿不到 pid、没有 stdin 管道；只能靠 WebView2 自己的心跳检测宿主存活，真机连续 3 代孤儿证明这条心跳不可靠。任务管理器"结束任务"（非"结束进程树"）只杀目标进程本身，不会级联杀子孙——Windows 上要做到这一点，必须显式用 Job Object 把子孙绑定到宿主进程的内核对象生命周期上，这件事此前完全没做。
2. **webServer(node.exe) 的陈旧端口清理在 Windows 上是完全失效的 stub**。`stale_web_server_port_holders`（`src-tauri/src/main.rs`）mac/linux 用 `lsof` 找谁占着我们的固定端口并清掉，但 Windows 分支此前是 `#[cfg(not(any(macos, linux)))] fn stale_web_server_port_holders(_port) -> Ok(Vec::new())`——**永远返回空**，等于「打包启动前清理上一代残留 webServer」这道保险在 Windows 上从未生效过。webServer 自身另有 stdin-EOF 自杀机制（`webServer.ts`），大多数场景能自愈，但这道保险本身是坏的，必须补。

两条成因需要两条不同的收割路径，**不能合并成一套**：webServer 有精确的身份证据（它绑定的固定端口，每个 Dev/生产槽端口不同，不会互相冲突）；WebView2 没有端口，只能靠 Job Object 枚举 + 身份核对，且身份核对不能只看镜像名——"msedgewebview2.exe" 不是我们独有的进程名，Teams/Outlook/系统 Edge 的 WebView2 全用同一个可执行文件（这一点是评审中第二轮被指出的：初版设计误判"这个文件名足够独特"，实际上一旦我们记账的 pid 被系统回收给别家应用的 msedgewebview2.exe——宿主重启后尤其常见——单靠镜像名核对会 taskkill 别人家的进程，见 §2.2 第三道核对）。

## 2. 改动摘要

全部改动在 `src-tauri/src/main.rs` + `src-tauri/Cargo.toml`（新增 Windows-only 依赖 `windows-sys 0.59`，特性 `Win32_Foundation`/`Win32_Security`/`Win32_System_JobObjects`/`Win32_System_Threading`）。

### 2.1 webServer：补齐 Windows 端口认领（复用已有机制，非新造）

- `parse_windows_netstat_port_holders`：解析 `netstat -ano -p TCP`，取本地地址端口精确等于目标端口的行的 PID。只匹配本地地址（天然排除"连到这个端口"的客户端连接）；不依赖 `LISTENING` 文案（规避非英文 Windows 本地化该词导致漏判）；用冒号前缀做 `ends_with` 匹配，不会被 8180/18180/81800 这类相似端口串味。
- `stale_web_server_port_holders` 新增 `#[cfg(target_os = "windows")]` 分支调用上述解析函数；原先的空 stub 收窄为仅覆盖 macOS/Linux/Windows 之外的未知平台。
- 调用侧**零改动**：`clear_stale_web_server_port`（已有 `taskkill /PID X /T /F` 分支）和 `spawn_web_server_recording` 的调用点完全不用碰，Windows 分支补上后自动生效。

### 2.2 WebView2：Job Object 只读枚举 + 认领文件收割（复用 PTY 孤儿收割模式，三道核对）

复用本仓已有的孤儿 PTY 收割设计（`src/host/services/terminal/terminalSessionManager.ts:143-152`）：落盘 `{pid, ownerPid, 身份标记}`，启动时核对后才收割，不新造语义。**评审两轮后从两道核对收紧到三道**（第二轮明确指出"镜像名足够独特"这个前提对 msedgewebview2.exe 不成立）：

- **Job Object 定位收窄为「只读枚举」，不设 `KILL_ON_JOB_CLOSE`**：`install_windows_process_containment()` 在 `main()` 最开头（早于 Tauri 创建任何窗口/webServer 子进程）把本进程加入一个匿名 Job。之后 WebView2 内部 `CreateProcess` 出的浏览器/GPU/渲染子进程默认继承 Job 成员身份（Windows 8+ 支持嵌套 Job，WebView2 不会给自己的子进程设 `CREATE_BREAKAWAY_FROM_JOB`）。**特意不设 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`**：如果设了，内核会在本进程句柄表被拆除的瞬间无条件杀光整个 Job（含 webServer），这会在「本进程正常退出但 webServer 优雅关库还没走完」的窗口里（例如应用内更新触发 restart）把 webServer 的 stdin-EOF 优雅关闭合同截断，在本可以善终的场景里制造硬杀——这正是 T1（更新流程优雅停机施工者）分析报告里明确要求本单避开的坑。Job 在本设计里唯一不可替代的价值是 `QueryInformationJobObject(JobObjectBasicProcessIdList)` 能拿到一份不受 pid 复用/父进程死亡影响的、内核维护的真实成员清单——这是 WebView2 子孙进程唯一可发现的入口。
- **落盘时机**：renderer 首帧就绪（`present_main_window`）后台线程调用 `capture_windows_process_claims`，枚举当前 Job 成员，逐个用 `tasklist /FI "PID eq N" /FO CSV /NH` 查镜像名，连同本实例的 WebView2 数据目录（`app_local_data_dir()`）一起写入 `<app_data_dir>/windows-process-claims.json`。选这个时机是因为此时 WebView2 的浏览器/渲染进程必已存在；如果真机验证发现有子进程是首帧之后才晚生（比如首次用到某个重量级 API 才触发新的 GPU 进程），会漏收，见下方遗留项。
- **纯函数 `claimed_windows_orphans`**（不摸文件系统/系统调用，喂伪造闭包即可单测），三道核对全过才收割：
  1. owner（记账时的宿主 Tauri 进程）现在必须已死；
  2. pid 现在的镜像名仍是 `"msedgewebview2.exe"`；
  3. **（红线加固）** pid 现在的完整命令行仍带着记账时的 WebView2 数据目录（`--user-data-dir=<绝对路径>`，`command_line_contains_data_dir` 做精确边界匹配——数据目录后必须紧跟分隔符/引号/结尾，不是任意子串，因此既不会漏判也不会被 `.dev`/`.dev2` 这类前缀撞上）。第 3 道专门堵住"pid 被系统回收给别家应用的 msedgewebview2.exe（Teams/Outlook/系统 Edge 都用这个进程名，宿主重启后尤其常见）"这个红线场景——此时第 1、2 道全部通过，只有第 3 道能识别出目标其实是别人家的进程。
  命令行通过新增的 `windows_process_command_line`（PowerShell `Get-CimInstance Win32_Process` 查 `CommandLine`）获取，只对已经通过前两道核对的候选 pid 调用，不是批量扫描。
- **`reap_stale_windows_processes`**：启动时（`.setup()`，spawn 新 webServer 之前）读回上一次的认领文件，跑 `claimed_windows_orphans` 判定，对命中的 pid 执行 `taskkill /PID X /T /F`，把收割掉的从账上抹掉、写回文件，落 `desktop-shell-stale-windows-process-reaped` shell event。

### 2.3 未采用的方案（及理由）

- ~~`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`~~：见上，会短路 T1 的优雅停机路径。
- ~~只凭镜像名核对 WebView2 身份（不加数据目录核对）~~：初版设计如此，评审后否决——见上方"红线场景"。
- ~~认领标识直接复用 `CODE_AGENT_TAURI_BOOT_TOKEN`~~：评估后放弃——它是注入给 webServer 的环境变量，Windows 上读取另一进程的环境变量需要侵入式的 PEB 读取（没有现成 API），没法拿来核对一个"活体"孤儿进程的身份；改用进程能自证的两样东西——镜像名 + 命令行里的绝对路径。
- ~~webServer 也走 Job Object 认领文件~~：见 §1，`"node.exe"` 太通用，端口认领是更精确的现成机制。
- ~~用进程创建时间（`GetProcessTimes`/`CreationDate`）核对 pid 是否被复用~~：与"数据目录精确匹配"是二选一的等价方案（评审里给出的两个选项之一），选了实现代价更低、且判据更直接（不止排除"pid 被复用"，还能排除"pid 恰好也是 msedgewebview2.exe 但不是我们的"）的数据目录匹配。

## 5. 需要 Windows 测试者复验的步骤

1. **编译**：确认 `windows-sys` 新依赖在真实 Windows 交叉/原生编译下能过（本单在 mac 上完全无法验证这部分，包括 `CreateJobObjectW`/`AssignProcessToJobObject`/`QueryInformationJobObject` 的具体调用签名、`JOBOBJECT_BASIC_PROCESS_ID_LIST` 变长数组的手工内存布局读取是否正确）。建议先跑一次 `build-windows-test.yml`（手动测试构建工作流）确认能过编译。
2. **端口认领回归**：打包安装后，用任务管理器强杀 `Agent Neo.exe`（模拟真机场景，"结束任务"而非"结束进程树"），确认 webServer 的 node.exe 子进程是否残留；若残留，重新启动 app，确认启动日志（`desktop-shell-events.ndjson`）里出现 `desktop-shell-stale-port-cleaned` 且旧 node.exe 被清掉、新实例正常起来。
3. **WebView2 认领收割回归**（核心验收项）：
   - 正常启动 app，等窗口出现后，任务管理器强杀 `Agent Neo.exe` 主进程（不要用"结束进程树"，否则测不出问题）。
   - 检查任务管理器里 `msedgewebview2.exe` 是否仍然残留（预期：**这次改动可能仍然残留**——Job Object 只是让它们变得可被下次启动发现并收割，不是让它们立即消失，因为本单刻意不设 `KILL_ON_JOB_CLOSE`）。
   - 重新启动 app，检查 `desktop-shell-events.ndjson` 是否出现 `desktop-shell-stale-windows-process-reaped` 事件，且事件里列出的 pid 与强杀前残留的 `msedgewebview2.exe` pid 一致；再用任务管理器确认这些 pid 确实已被清理。
   - 打开 `<数据目录>/windows-process-claims.json`（生产 `%APPDATA%\<identifier>`），确认里面记录的是本次启动捕获到的 webview2 pid 列表（而不是空的——空说明 Job Object 枚举没生效，需要排查），每条记录应带 `dataDir` 字段（本实例的 `app_local_data_dir()` 绝对路径）。
   - **红线场景（若条件允许，优先验）**：同一台机器上另开一个会用到 msedgewebview2.exe 的应用（Teams/Outlook/Edge 均可），确保它当前也有活跃的 msedgewebview2.exe 进程；强杀 Agent Neo 后，观察收割逻辑是否只清理 Agent Neo 自己认领文件里记录、且命令行仍指向 Agent Neo 数据目录的那些 pid，**绝不能碰到 Teams/Outlook/Edge 自己的 msedgewebview2.exe**——这是本单第二轮评审专门要求补的判据（三道核对里的第 3 道：命令行精确匹配数据目录），务必验证它真的挡住了跨应用误杀。
4. **多槽并存不误伤**：Dev 包（`.dev`/`.dev2` 等不同 identifier）与生产包同时跑，强杀其中一个，确认收割只清理被杀那个的残留进程，另一个仍在正常运行的实例（webServer 端口不同、WebView2 认领文件路径按 `app_data_dir()` 天然按 identifier 分目录）不受影响。工单要求的"mac Dev 包真机验证不误伤"——本单**没有改动任何 mac 分支的代码路径**（`stale_web_server_port_holders`/`clear_stale_web_server_port` 的 mac 分支、`cleanup_server`/`terminate_child` 均未触碰），逻辑上不存在回归风险；已跑 `cargo test` 全量确认 mac 编译路径无破坏，未额外打包 Dev 包做真机验证（改动面 0 命中 mac 运行时代码）。

## 7. 遗留项

1. **Windows 真机编译/运行验证是完全的空白**——本机无法交叉编译到 Windows（`ring` 原生构建脚本依赖），所有 Win32 API 调用的正确性目前只靠对着官方文档和 `windows-sys` 0.59.0 源码核对签名，未经任何形式的真实执行验证。这是本单最大的风险点，见 §5。
2. **WebView2 子孙进程捕获时机是单点快照**（renderer 首帧就绪后一次），如果某些 GPU/渲染子进程是应用运行较久之后才新生（例如首次使用某个重量级渲染路径），会漏收进认领文件。如果真机验证发现有残留 pid 不在认领文件里，需要补一个周期性刷新或在更多生命周期节点重新捕获。
3. Job Object 的 `QueryInformationJobObject` 固定给了 128 个 pid 的缓冲区上限（`MAX_TRACKED`），正常场景远够用；如果真机出现异常多子进程导致截断，`NumberOfProcessIdsInList` 会小于 `NumberOfAssignedProcesses`，静默丢失多出的部分，不会崩溃但会漏收。
4. 未触及 T1 报告里提到的独立缺陷（C1 编译缓存预热对 Windows 更新路径从未生效过）——不在本工单范围。
