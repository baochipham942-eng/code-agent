## 结论先说

第 1 步的量化**部分推翻了工单方案**，范围随之缩小：

| 工单原计划 | 量化后实际做的 | 为什么变 |
|---|---|---|
| A：`_meta` 压到「100 token 出头」，砍掉 `targetContext` / `expectedOutcome` | 只压描述文本，**三个字段全留**，277 → 182 token | 工单认为这两个字段「绝大多数工具用不上」的依据（历史填充率 1%）是 **`_meta` 剥离 bug 造成的假象**；#997 修好后真实填充率 42.8% / 39.5%，且都在 UI 上被渲染 |
| B 第 1 件：schema 侧普遍设 `additionalProperties: false` | **不做** | OpenAI 系已经在转换层（`normalizeJsonSchema`）自动补上了，铺到源 schema 对模型零增益；而 executor 今天对未声明字段是硬拒，铺开 = 一次性把 140 个工具翻成硬拒 |
| B 第 2 件：宿主侧校验分档 | **照做**，是本批唯一的行为改动 | 量化确认了工单的判断，且给出了硬数字 |

净改动：4 个生产文件（其中 1 个只改注释性常量文本）+ 2 个测试文件。

## 1. 第 1 步量化（三项，全部实测）

### 1.1 OpenAI 系 provider 有没有等价的工具定义缓存？

**没有显式缓存控制，只有各家的自动前缀缓存，且覆盖不全。**

- 代码侧：只有 `claudeProvider.ts:479` 在 tools 数组末尾打 `cache_control: {type:'ephemeral'}`。
  OpenAI 系走 `convertToolsToOpenAI`，全仓没有任何等价声明。
- 真实账本（`usage_ledger`，真库 + dev 库合计）：

  | provider | 记账条数 | 全价 input | 缓存命中 | 命中占比 |
  |---|---|---|---|---|
  | zhipu | 432 | 9,130,273 | 3,505,792 | 27.7% |
  | deepseek | 356 | 5,383,289 | 3,207,040 | 37.3% |
  | custom-tokenrhythm | 94 | 1,192,507 | 830,336 | 41.0% |
  | minimax | 178 | 2,277,790 | 0 | **0.0%** |
  | custom-team-relay | 1 | 25,577 | 0 | 0.0% |

**结论**：A 的收益不能按"有缓存兜着"打折——60~70% 的 input token 仍按全价走，
minimax 完全没有缓存。A 的优先级维持，不下调。

### 1.2 `additionalProperties: false` 铺开后，会有多少调用被判「有多余字段」

拿真库 20,179 次真实工具调用逐条比对 `arguments` 的键 vs 该工具 schema 声明的
`properties`。**先剔除宿主自己加的字段**——`content_length` / `content_lines` /
`old_text_length` / `new_text_length` 是 `sanitizeLargeTextToolArguments`
（`src/shared/utils/browserComputerLargeTextRedaction.ts:55`）在落库前补的展示字段，
根本不经过 validator。不剔除就是把自己的显示逻辑当成模型错误（初版统计里它们占了
"多余字段"的一半以上）：

| 窗口 | 可比对调用数 | 带 `_meta` 残留（我们自己的洞） | 模型自造字段 |
|---|---|---|---|
| 2026-07 起 | 5,327 | 2,779（**52.2%**） | 528（9.9%） |
| 2026-08-06 起 | 362 | 26（7.2%） | 6（1.7%） |
| #997 合 main（08-06 19:34）之后 | 94 | 0（0.0%） | 0（0.0%） |

- 26 条 08 月残留的时间戳全部落在 **08-06 19:34 之前**（`toolCallMeta.ts` 由 #997 引入）。
  也就是说 `_meta` 泄漏这条洞确实被 #997 堵上了。
- **但 n=94 太小，不足以宣称 0%**（按 rule of three，95% 置信上界约 3%）。
  这个数字只能当"没有反证"用，不能当"风险已消失"。
- 模型自造字段是真实存在但很小的一类：`maxChars` / `max_length` 打到 WebFetch
  （真字段叫 `max_chars`）；历史上还有 481 次把 `_meta` 写成 `meta`、以及
  `_auto_extract`、`-i`、`glob` 之类。

**结论**：工单的分档判断成立，且拿到了硬数字——**硬拒方案在 7 月那个窗口会打掉
一半以上的工具调用，而其中 84% 是我们自己没剥干净的 `_meta`，不是模型传错**。

### 1.3 `_meta` 瘦身前后的真实 token 差

用仓库自己的 encoder（`gpt-tokenizer`，与 `tokenEstimator` 同款），不用字符数估：

| 项 | 数值 |
|---|---|
| 工单估的 `_meta` 体积 | 801 字符 ≈ **430 token**（高估 55%） |
| 实测 `META_PROPERTY_SCHEMA` | **277 token**（OpenAI 路径过 `normalizeJsonSchema` 后 287） |
| `CORE_TOOLS` 数量 | **22**（工单写的 23） |
| 22 个核心工具定义本体（不含 `_meta`） | **7,473 token** |
| `_meta` 注入总开销 | 277 × 22 = **6,094 token** |
| **`_meta` 占核心工具整包** | **44.9%** |
| 瘦身后 | 182（OpenAI 192）→ 22 个合计 4,004 |
| **每请求净省** | **约 2,090 token** |

绝对值比工单估的 9.9K 小，但**相对占比比工单说的更严重**——工具定义包里几乎一半
是这段元数据。

## 2. 量化推翻了什么（这一节是本报告的重点）

### 2.1 A：不能砍 `targetContext` / `expectedOutcome`

工单的依据是历史填充率 `targetContext` 1.1% / `expectedOutcome` 1.0%，据此判定
「绝大多数工具用不上」。**这个 1% 是 `_meta` 剥离 bug 的产物，不是模型行为。**

按时间切片看得很清楚（`messages.tool_calls`，两库合并）：

```
月份         调用数  short%  target%  outcome%  _meta残留%
2026-05        2359   63.2     8.3      7.7       22.2
2026-06        3273   73.1     0.0      0.0       88.7
2026-07        4723   97.5     0.0      0.0       53.7
08-06 全天      362   87.0    42.8     39.5        7.2
#997 之后        94   92.6    53.2     36.2        0.0   ← 剥离链路修好
```

剥离链路修好之前，语义字段压根没被提到 envelope 顶层，所以落库看着像"模型不填"。
修好之后 42.8% / 39.5%（#997 之后那 94 次是 53.2% / 36.2%）。而且两个字段都在被消费：

- `targetContext` → `TargetContextIcon.tsx` 按 `kind` 渲染图标（app/browser/mcp/file/memory）
- `expectedOutcome` → `toolExecutionPresentation.ts:263` 的 `errorWithOutcome` 报错文案

砍掉它们不是"减冗余"，是**删一个正在跑的 UI 能力**。所以 A 改成只压描述文本，
结构一字不动，省 2,090 token/请求（原目标 4,268，差额就是这两个字段的价钱）。

**一个附带发现（本批没做，留给后续判断）**：模型填的 `targetContext` 质量两极——

- 18.7% 的 `label` 就是工具名本身（零信息，如 `{"kind":"browser","label":"WebSearch"}`）
- 18 个工具里 **7 个 kind 自相矛盾**：`Bash`→file/app、`WebSearch`→browser/mcp_server、
  `AskUserQuestion`→app/file/memory、`task_status`→memory/file、`spawn_task`→file/memory/app
- 另外 11 个 kind 稳定且正确：Read/Write/Edit/Append/Glob/Grep/ListDirectory→file、
  WebFetch→browser、MemoryWrite→memory —— **而这 11 个恰恰是宿主自己就能推出来的**
  （Read 的目标就是 `params.file_path`）
- `iconHint` 只填了 8.4%

也就是说：`targetContext` 要么宿主能免费推导，要么模型猜不准。真正省 token 的做法
是**宿主推导 + 从 schema 里拿掉**，但那是新建一张推导表，超出本工单范围，没做。

### 2.2 B 第 1 件：不是"可以放开做"，是"做了会踩雷"

工单把两件事分开说：schema 声明 `additionalProperties: false`（帮模型）vs 宿主校验
（管执行）。**在当前代码里这是同一个开关**：

1. `shared.ts` 的 `normalizeJsonSchema` 已经给每个 `type:'object'` 节点补
   `additionalProperties: false`，且 `convertToolsToOpenAI` 必过这一步。
   **OpenAI 系 provider 收到的 schema 早就带边界了**，铺到源 schema 零增益。
2. `toolExecutor.ts` 对 `validateToolInputSchema` 的**任何** issue 直接
   `return { success: false }`。源 schema 上写 `additionalProperties: false`，
   就等于同时打开了这条硬拒。

现状佐证：145 个工具里只有 5 个声明了 `false`（`computer_use` / `spawn_task` /
`steer_task` / `cancel_task` / `task_status`）——#985 正是撞在这 5 个里。

所以**顺序必须反过来**：先做分档，再谈铺开。本批只做分档，不铺 schema。
（Claude 路径没走 `normalizeJsonSchema`，要不要补是独立一行的事，没做——Anthropic
没有 strict function calling，那只是个提示，还要额外掏 token，不值当。）

## 3. 实际改动

### A. `src/host/model/providers/shared.ts`
`META_PROPERTY_SCHEMA` 的描述文本压缩，字段结构与 `required` 一字不改。
顶上留了注释写明这是每工具复制一份的常驻开销、以及为什么这三个字段不能删。

### B. `src/host/tools/toolSchemaValidator.ts`
新增 `stripUndeclaredToolParams(inputSchema, params)` → `{ params, removedPaths }`。
只在 `additionalProperties === false` 的对象节点上剥，与 `validateSchemaNode` 同一个
判定条件、同一套路径口径——**validator 报了什么，这里就剥什么**，两边不会漂。
递归覆盖嵌套对象和数组元素。

### C. `src/host/tools/toolExecutionTelemetry.ts`
新增 `reportUndeclaredToolParams()`：

- 生产档：往当前 tool span 上打 `tool.undeclared_params`（键名）+ `..._count`，
  best-effort，永不改变执行；
- 开发档（`NODE_ENV !== 'production'`）：额外 `console.error` fail-loud，与 P0-2
  投影层登记制同构。判据沿用仓库既有口径（`logger.ts:179`、`appPaths.ts:152` 都用
  `NODE_ENV === 'production'` 判生产）——**若打包产物没设 NODE_ENV，这里和 logger
  会一起退到 dev 行为**，是既有约定，不是本批引入的；
- **只记工具名 + 键名，不记值**（入参里可能有路径、命令、文件内容）。

### D. `src/host/tools/toolExecutor.ts`
唯一的行为改动，在 `validateToolInputSchema` 调用点：

```ts
const blockingIssues = schemaIssues.filter((i) => i.category !== 'additional_property');
if (blockingIssues.length > 0) { /* 照旧硬拒，错误文案只带 blocking 部分 */ }
if (schemaIssues.length > 0) { /* 剥离 + 上报，然后放行 */ }
```

`type_mismatch` / `enum_mismatch` / `format_mismatch` / `missing_required` 全部维持硬拒。
剥离发生在权限判定、directive-memory 路径权威、policy 检查**之前**，所以那些环节
读到的都是已剥离的入参。

| 变异 | 预期 | 实际 |
|---|---|---|
| 分档改回硬拒（`blockingIssues = schemaIssues`） | 分档用例转红 | **6 条红**，其余 17 条绿；还原后 23/23 绿 |

> 变异 2 第一次跑出来是**绿的**——因为替换串的缩进对不上，改动压根没落到文件里。
> 补了 `assert MUTATION TARGET NOT FOUND` 才发现。变异验证必须先确认变异真的生效，
> 否则"变异后仍绿"会被误读成"门守不住"，或者更糟——被误读成"这门很稳"。三轮变异
> 现在都带这条断言。

### 守不住的部分（如实写）

- **体积门只钉 `_meta` 这一个常量**，不管工具自己的 `description` 和 `inputSchema`
  往里塞多少字。全包体积（当前 7,473）没有门。
- **`stripUndeclaredToolParams` 只对声明了 `additionalProperties: false` 的 5 个工具
  生效**。另外 140 个工具没声明边界，多余字段照旧原样透传给工具（与改动前一致，
  工具自己忽略）。这不是漏洞——没声明边界就没有边界——但别把这条门当成"全仓都
  拦住了"。
- **剥离对模型是静默的**。硬拒会给模型一个"你写错了"的纠错信号，剥离不会。
  对 `maxChars` 这类模型自造字段（真库 1.7%），改动后模型不会被告知它写错了。
  取舍是有意的：140 个未声明边界的工具本来就是静默忽略，剥离让 5 个声明了边界的
  工具与它们行为一致；诊断信号改由 telemetry + 开发档 fail-loud 承担。
- **`#997 之后 0/94` 不能读成"`_meta` 泄漏风险已归零"**，样本量只支持"上界约 3%"。
- **`tool.undeclared_params` 这条 telemetry 只在有 active tool span 时落得下**
  （`findToolSpan` 拿不到 span 就静默跳过）。开发档的 `console.error` 不受此限。
