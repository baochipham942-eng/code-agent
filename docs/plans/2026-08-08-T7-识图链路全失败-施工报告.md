## 一、真机根因判定

`host-logs/code-agent-2026-08-07.log` 中三次 `[Fallback]` 告警**都没有任何一条"视觉预处理失败（provider/model）"的逐候选日志**——这是关键信号：说明当时 `getVisionPreflightCandidates()` 返回的候选数组是**空的**（零候选），而不是"候选都试过了但失败了"。

比对 `config.redacted.json`：

- `models.routing.vision = { provider: 'xiaomi', model: 'mimo-v2-omni' }`（用户在设置里选过识图模型）
- 但 `models.providers` 里，**只有 `longcat` 和自定义 endpoint 显式带 `apiKeyConfigured: true`**；`xiaomi`、`zhipu`、`deepseek`、`claude`、`moonshot` 等条目只有 `enabled: true`，没有这个字段
- `cloud.enabled: false` → 排除了"云端托管 key 兜底"这条路（`configService.getApiKey` 的第三优先级）
- 读代码确认：`mimo-v2-omni` 确实 `supportsVision: true`（`providerRegistryAdditional.ts:215-220`），`getVisionPreflightCandidates` 的 `pushCandidate` 要求 `configService.getApiKey(provider)` truthy才会入选（`modelRouter.ts:320`）

**结论：该用户选了 xiaomi/mimo-v2-omni 作为识图模型，但从未填过 xiaomi 的 API Key（其它 provider 同样零 Key）。** 这是"设置里选了模型，但没意识到还要单独配 Key"的典型陷阱，不是网络/超时/模型下线一类瞬时故障。

顺带发现（未改，非本单范围）：`modelRouter.ts:314` 注释说排除 `glm-4.6v-flash`（"不支持 base64"），但读 `providerRegistryBase.ts:456-472` 该模型 `visionCapabilities.supportsBase64` 现在是 `true`——排除逻辑已经不生效，注释是历史遗留，不影响本次判断（zhipu 本来就没配 Key）。

## 二、识图预处理全失败的成因谱系（枚举）

| 成因 | 现象 | 本次修复后的用户可见提示 |
|---|---|---|
| **零 Key**（选了模型没填 Key / 从没接触过设置页） | `getVisionPreflightCandidates()` 返回 `[]`，日志无逐候选记录 | toast：「还没有配置支持读图的模型，去设置里加一个」+「去配置识图模型」按钮直达设置-模型页 |
| Key 已配但失效/过期 | 候选存在，调用报 401/403 | 分类为 `auth`，toast 归入"暂时都调不通" |
| 需代理的 provider 在无代理环境（如国际 provider 但用户机器没代理） | 候选存在，调用报 network/timeout | 分类为 `network`/`timeout` |
| 触发限流/额度耗尽 | 候选存在，调用报 429/402 | 分类为 `rate_limit`/`quota` |
| 模型下线/被下架 | 候选存在，调用报 404/model not found | 分类为 `model` |
| 图片本身导致模型拒答（返回空内容） | `preflightImagesForMainModel` 返回 `null`（非 throw），当前循环继续试下一个候选，不计入失败明细——这是既有行为，本单未改 | 与"零候选"同一兜底文案（因为 attempts 数组不会记录这类 null 返回） |

## 三、改了什么

### 1. Provider 级错误日志（主修复）

- `src/host/agent/runtime/contextAssembly/inferenceProviderFallback.ts` 新增：
  - `VisionPreflightAttempt`（provider/model/category/detail）
  - `classifyAndLogVisionPreflightFailure`：复用已有的 `classifyProviderFallbackReason`（timeout/rate_limit/quota/auth/provider_unavailable/network/model/unknown），不是另起一套分类
  - `logVisionPreflightExhausted(hadCandidates, attempts)`：**区分"零候选"和"候选都失败"两句不同的日志**，不再是一句笼统的"所有已配置的识图模型预处理均失败或不可用"（这句话在零候选场景下本身是误导——压根没有"已配置"的候选）
  - `broadcastVisionPreflightUnavailable`：把结果广播到已上线的 `provider:fallback` IPC 通道
- `src/host/agent/runtime/contextAssembly/visionPreflight.ts` 新增 `runVisionPreflightCandidates`：把"依次尝试候选 + 记录逐个失败"的循环从 `inference.ts` 搬过来（原地实现会把 `inference.ts` 推过 `max-lines: 1000` 门），职责上也更对——这是"识图预处理"自己的关注点。

现在真机复现同一场景，日志会是：

```
[Fallback] 未找到已配置 API Key 的识图模型（零候选），图片将转换为文字描述
```

而不是原来那句看不出问题在哪的：

```
[Fallback] 所有已配置的识图模型预处理均失败或不可用
```

若候选存在但报错，日志会带 provider/model/分类：

```
[Fallback] 视觉预处理失败（zhipu/glm-4.6v-flash, category=auth）：401 Unauthorized: invalid api key，尝试下一个识图模型
...
[Fallback] 所有已配置的识图模型预处理均失败或不可用（尝试了 1 个：zhipu/glm-4.6v-flash[auth]）
```

### 2. 零 Key 兜底体验（用户可见提示）

排查发现：`inference.ts` 里已有的"识图预处理成功/失败"提示走的是 `ctx.runtime.onEvent({ type: 'notification', ... })`，而**这个事件类型在渲染侧没有任何订阅者**（`useConversationStreamEffects.ts` 的大 switch 没有 `case 'notification'`，全仓 grep 找不到第二个消费方）——包括本单要修的"全失败"场景，也包括工单之外、已经存在的"预处理成功"提示，两条路都是静默丢弃，用户实际上从来没看到过这些消息。

选择复用另一条**已经真正跑通**的通道：`provider:fallback` IPC（`ProviderStatusNotice.tsx` 订阅并弹 toast，此前只用于"模型间自动降级"场景）。新增两个 category：

- `vision_no_key`：零候选 → toast「这张图片没能被识别：还没有配置支持读图的模型。去设置里加一个识图模型（免费的智谱 GLM-4.6V Flash 也可以）。」+「去配置识图模型」按钮（点击 `openSettingsTab('model')` 直达设置-模型页）
- `vision_unavailable`：候选都失败 → toast「这张图片没能被识别：已配置的识图模型暂时都调不通，可能是网络或额度问题，稍后再试或去设置检查一下。」

文案对非程序员友好（不提 provider id / API Key 这种术语，说"没有配置支持读图的模型"），en/zh 同步写在 `src/renderer/i18n/notices.ts`。

### 3. 未修的相邻问题（如实记录，不在本单范围）

- `notification` 事件全渲染侧无消费者是一个更大的既有缺口（至少 3 处调用点受影响：本单改前的识图失败提示、识图成功提示、工具不支持提示 `inference.ts:719-724`）。本单只把"识图全失败"这一条改道到确实能到达用户的 `provider:fallback` 通道，没有去修 `notification` 这条通道本身——那是另一个更大范围的改动，建议单独立单。
- `preflightImagesForMainModel` 返回 `null`（模型答复为空）时不算作"失败"，不会进入 `attempts` 数组，也不会被单独分类——这类情况目前会被兜底成"零候选"同一句文案（因为它不产生 attempts 记录）。真实概率较低（多数 provider 拒答会抛错而不是返回空字符串），未特殊处理。
