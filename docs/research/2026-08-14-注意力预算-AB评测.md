# 注意力预算瘦身 A/B 评测（N-L8-ATT5）

> 2026-08-14 · 验证 #1130（去重七连）+ #1131（_meta 信封退役）**有没有让模型变笨**。
> 前置报告：`2026-08-14-注意力预算-真实下发五桶分解.md`（ATT1）。

## 结论

**没有任何证据显示 #1130 + #1131 的瘦身让模型变笨；同时瘦身在成本面有可观测收益。**

三条，按证据强度排：

1. **能力面未观察到退化**。两档模型共 **82 个有效配对**，能力判据（capability / score）上只有 **3 对**出现差异（post 赢 1 / pre 赢 2，p=1.0000）——强档 46 对**全部打平**，零 decisive pair。
   ⚠️ 这是「**未观察到退化**」，不是统计意义上「非劣性成立」：79/82 打平是天花板效应，decisive pair 太少，sign test 没有功效去证明"等价"。**要证明非劣性需要换有读数空间的判据**，不是加样本量。
2. **效率面无显著差异**：turnCount / toolCalls / duration 在两档上 p 值均不显著（最低 0.0652，弱档 duration）。
3. **成本面瘦身有实测收益**：两档的 `cost_exceeded`（case 自带 $0.1 上限）都是瘦身前更多——弱档 **pre 5 : post 1**，强档 **pre 16 : post 11**；强档"仅 pre 被剔"的 8 条里 **7 条是成本超限**（$0.1010–$0.1254）。同一 case、同一上限，上下文更大的那一臂更容易撞穿。

⇒ **瘦身可以放心保留。**

## 一、工单前提被推翻：`--compare` 造不出这单的回滚臂

工单假定用 `scripts/eval-ci.ts --compare <yaml>` 造两臂。as-built 实测不成立。

`src/host/testing/comparator/runCompare.ts` 明确声明执行链路只消费 4 个字段：

```
CONSUMED_COMPARE_FIELDS   = model / provider / systemPrompt / harness
UNCONSUMED_COMPARE_FIELDS = enabledTools / temperature / agentConfig   ← 写了会被当假区分特征拦掉
```

其中唯一能表达提示词差异的 `systemPrompt`，经 `scripts/eval-ci.ts:681` 变成
`systemPromptOverride`，而它在 `src/host/testing/agentAdapter.ts:457` 只替换
`SYSTEM_PROMPT`（即 `buildPrompt()` 的输出）这一段。

本次瘦身横跨 7 个源文件，其中 `providers/shared.ts` 的 `_meta` 逐工具 schema 注入、
`taskManager.schema.ts`、`nudgeManager.ts`、`contextBuilder.ts`、`tokenOptimizer.ts`
**都在 `systemPromptOverride` 的射程之外**。

在两棵真实代码树上各跑一次 `buildPrompt()`（同一份 `~/.code-agent/SOUL.md`，同一进程口径）：

| 瘦身后 `att5-post` | `e7cadcd89`（当前 main） | 18667 | **6222** |

**泛化**：任何跨 tool schema 层的 A/B 都不能用 `--compare` 造臂。

## 二、改用的造法：双 worktree 同时间窗并行

| | |
|---|---|
| 两臂 | `.worktrees/att5-pre` = `b668b7ded` / `.worktrees/att5-post` = `e7cadcd89` |
| 差异 | 整棵编译产物，不经任何注入点或运行时开关 |
| 调度 | 两臂**同时启动、同时间窗并行**（非"跑完 A 再跑 B"），消除时间漂移 |
| 用例 | 两臂都用 `--case-dir` 显式指向主仓同一份 `.claude/test-cases` |
| 结果 | 各自落 worktree 内 `.code-agent/test-results/`（gitignore，互不污染） |

这条路在本仓有既有资产（`infra_neo_eval_abab_harness`），其中一条既有结论正是
**"别用 override 机制做 A/B"**。

### 关于两个准入断言

工单要求 `assertCompareArmsDistinct` / `assertCompareArmsActivated` 必须真跑到。
双树造法用不上 `runCompare`，故用等价实证满足其立意：

| 断言 | 立意 | 本单的等价证据 |
|---|---|---|
| `assertCompareArmsDistinct` | 防 X vs X | 两臂 git sha 不同 + 上表 `buildPrompt` 6903 vs 6222 实测差 |
| `assertCompareArmsActivated` | 防"无数据冒充势均力敌" | 分析脚本剔除 `infra_excluded/skipped/cost_exceeded` 后显式报有效配对数，为 0 则判"结论不成立" |

`scaffoldProfile` 轻/重档 A/B 恰好**能**走 `--compare`（`harness` 是被消费字段，两个断言在
那边真跑得到），但它与本单核心问题正交，建议拆独立一单。

## 三、判据：不能用 pass/fail

07-15 实测的**天花板效应**：cowork 用例在旧提示词下就 18/19 pass，断言是
`file_exists` / `content_contains`——测"最后有没有产出文件"，测不到"怎么开场"。
pass/fail 对提示词改动没有读数空间。

改用连续/序数指标 + 配对 sign test（与 `comparator/signTest.ts` 同公式：精确二项、
双尾、只计 decisive pair）：

| 指标 | 方向 | 作用 |
|---|---|---|
| `capability`（passed=2/partial=1/failed=0） | 越高越好 | 主判据 |
| `score` | 越高越好 | 主判据 |
| `turnCount` | 越低越好 | 效率 |
| `toolCalls` | 越低越好 | 效率 |
| `duration` | 越低越好 | **辅助，不进能力判定**（见混杂因素） |

`infra_excluded` / `skipped` / `cost_exceeded` 任一侧出现即整对剔除——它们是环境噪声与
成本闸，不是能力信号。

两臂之间隔了 10 个 commit，不只有瘦身。逐类核过：

| 类别 | 文件数 | 对 eval 的影响 |
|---|---|---|
| 瘦身本身（#1130/#1131/#1133） | 15 | **这是自变量** |
| 语音全族（#1128 打断判定链、#1134 L7 声纹） | 16 | eval 不跑语音，零影响 |

| shell 链 #1135（删零 importer 死导出） | 1 | 纯删除，零行为 |
| shell 链 #1136（`terminalSessionManager`） | 2 | eval 不开终端会话 |
| shell 链 #1129（PTY 能力探测改真 spawn 一次） | 1 | **唯一有行为的**：可能影响 `duration`，不影响模型决策 |

⇒ `duration` 标注为受 #1129 污染，只作辅助读数，不进能力判定。其余混杂对本单判据无效应。

**评测基础设施两臂一致**：施补丁前 diff 过，`b668b7ded` 与 `e7cadcd89` 的
`scripts/eval-ci.ts` 除下节那一个 hunk 外完全相同；随后把 post 版整个覆盖到 pre 树，
两臂该文件现字节一致。

### eval 路径与产品路径的两处已知分叉

本单撞到两条，都是同一形态——**eval 路径拿到的不是用户真实运行环境**，做基线时要留神：

### skill 别名注入：eval 路径天然屏蔽

邻会话（ATT7）在**产品路径**真机量到：轮首 skill 别名命中会把整份 SKILL.md 塞进首个
system message，同一通话静态桶在 9911 与 11168 之间摆动（差 1257 token）。

本单 eval 路径不受此影响，因为链被一行 env 关掉了：

- `scripts/eval-ci.ts:468` `prepareRealEvalRuntime()` 里 `CODE_AGENT_INCLUDE_CLAUDE_LEGACY_SKILLS ||= 'false'`
- `skillDiscoveryService.ts:38` `shouldIncludeClaudeLegacySkills()` 无 env 时 **默认 true**，被这个 falsy env 显式压成 false

⇒ **产品路径默认开、eval 路径默认关**。两句话是同一件事的两端：eval 的数字干净，
产品路径的 1257 token 才是用户每一轮真实承担的成本。

**这条对预算基线的含义比 1257 本身更重要：棘轮门 / 预算基线若取自 eval 路径，
天然看不见用户级 skill 这一整块。**（已同步 N-L8-ATT10。）

Neo 自己的 skill（非 claude legacy）不受该 env 控制，仍可能命中别名；但两臂读同一份
case、同一套 skill 目录，命中是确定性的、两臂同等，配对设计下只增噪、不引入臂间偏差。

## 六、顺路修：`AUTO_TEST_BASE_URL`

跑量前撞到一堵墙：任何走 `StandaloneAgentAdapter` 的 headless 进程都抛
「无法解析 provider 的 baseURL」，而 app 内选同一个中继 provider 能正常跑（邻会话 ATT7
当天就在用），所以不是 key 的问题。

`providerResolution.ts` 的通用分支里，动态 custom provider（`custom-xxx`）的端点**唯一
来源**是 `getSettingsProviderBaseUrl()` → `getConfigService().getSettings()`，而它在
headless 进程里只返回 17 个内置 provider，`custom-*` 一个都不在。

### 根因：`configService.initialize()` 在 headless 路径从未被调用

> ⚠️ 初版报告把这里写成「`getSettings()` 对 `models.providers` 做白名单过滤」——**那是从
> 现象反推的，错的**。`getSettings()` 只是 deep clone，`mergeSettings` 是无过滤递归合并。
> 下面是变异验证给出的实证。

`ConfigService` 的 `this.settings` 初值是编译进代码的 `DEFAULT_SETTINGS`（正好 17 个内置
provider），只有 `await initialize()` 才会去读 `~/.code-agent/config.json` 并合并进来。

变异验证（同一进程内前后对比）：

| 时点 | providers 数 | 含 `custom-tokenrhythm` |
|---|---|---|
| `initialize()` 前 | **17** | 否 |
| `initialize()` 后 | **24** | **是** |

`configPath` 本身是对的（实测 `/Users/linchen/.code-agent/config.json`），问题纯粹是没人调初始化。

全仓调用点普查：

| 入口 | 调 `initialize()` | 结果 |
|---|---|---|
| `src/web/webServer.ts:448` | ✅ | 拿得到 custom provider |
| `src/cli/bootstrap.ts:163` | ✅（`initMainConfigService()` + await） | 拿得到 |
| eval-ci / `StandaloneAgentAdapter` | ❌ | 停在 DEFAULT_SETTINGS |

⇒ **这不是产品级问题**，产品两条入口都初始化了；只影响评测与独立脚本路径。

### 为什么本单不直接补那一行

给 `prepareRealEvalRuntime()` 加一句 `await initialize()` 就能修，但那会让**评测结果依赖
本机用户配置**（provider 列表、温度、模型默认值都会漂进来），可复现性下降。现状究竟是
疏漏还是有意为之，是个设计权衡，不该在评测单里顺手拍板——已立 **N-PROV1** 交由该单决策。

本单只补齐 `AUTO_TEST_*` 家族缺的一项（`AUTO_TEST_PROVIDER` / `AUTO_TEST_MODEL` /
`AUTO_TEST_API_KEY` 早已存在，独缺 base url），显式注入、不改任何默认行为：

```ts
const baseUrl = process.env.AUTO_TEST_BASE_URL;
// modelConfig 已是 `& Partial<ModelConfig>`，本就接受 baseUrl，只是没人传
```

若 N-PROV1 决定"评测就该读用户真实配置"，这个显式入口仍有价值——它能覆盖到用户配置里
没有的临时端点。

本单的修法是补齐 `AUTO_TEST_*` 家族缺的一项（`AUTO_TEST_PROVIDER` / `AUTO_TEST_MODEL` /
`AUTO_TEST_API_KEY` 早已存在，独缺 base url），不动 provider 解析本身：

```ts
const baseUrl = process.env.AUTO_TEST_BASE_URL;
// modelConfig 已是 `& Partial<ModelConfig>`，本就接受 baseUrl，只是没人传
```

### 剔除对照（差集本身是信号）

剔除不是随机缺失——它按臂各自发生，谁更容易被超时/成本闸打穿，在同一负载下是相对量。

| 档 | pre 剔 | post 剔 | 两臂都剔 | 仅 pre | 仅 post | 差集 p |
|---|---|---|---|---|---|---|
| 弱 | 18 | 29 | 13 | 5 | **16** | 0.0266 |
| 强 | 20 | 16 | 12 | **8** | 4 | 0.3877 |

重叠窗口口径（只算两臂都还在跑的那段内启动的 case，切掉先收臂让出的带宽红利）：

| 档 | pre 剔除率 | post 剔除率 |
|---|---|---|
| 弱 | 25.7% (18/70) | 40.0% (26/65) |
| 强 | 28.6% (20/70) | 22.9% (16/70) |

**两档方向相反，且弱档那条与 duration 自相矛盾**（弱档 post 在跑成的 case 上更快，24:12 / 均值 -2459ms，却被超时闸打穿得更多）。判为中继并发波动，**不作能力结论**。

但**成本闸这一侧方向是一致的**：强档"仅 pre 被剔"的 8 条里 7 条是成本超限
（`multiagent-parallel-search` $0.1254、`multi-turn-build-on-previous` $0.1090、
`cross-file-consistent-edit` $0.1085 …），"仅 post 被剔"的 4 条里只有 3 条；
弱档 `cost_exceeded` 是 5:1。这是瘦身收益的直接读数。

## 九、方法论产出（给后续单）

1. **跨 tool schema 层的 A/B 不能用 `--compare` 造臂**——表达率只有 17%，见 §一。
2. **pass/fail 对提示词改动没有读数空间**，天花板效应实测重现：强档 46 对全平。要证明非劣性得先有能区分的判据（LLM judge 评开场质量、或直接对首轮 token 分布做检验），加样本量无用。
3. **剔除是有信息的，别当噪声丢掉**：按臂统计差集 + 对差集本身跑 sign test；两臂同时启动时，先收的那臂会把带宽让给后收的臂，需用重叠窗口口径校正。
4. **基元中继适合不卡时限的活，不适合带超时闸的批量跑**：单发不慢（邻会话 ATT7 实测 6.6–13.6s），慢在并发排队。批量跑要么并发压到 1–2，要么用 `CODE_AGENT_FORCE_TIMEOUT` 抬闸。
5. **`--model` 必须配 `--provider`**：只给 model 会落到 `DEFAULT_PROVIDER`（longcat），把 A 家模型名发给 B 家端点，报 `Unsupported model` —— 看着像模型不存在，实际是 provider 串了。
