## 口径与证据边界

- 抓取点是 provider 转换完成后的最终发送边界：chat-completions 为 `AiSdkAdapter → makeAiSdkFetch`，Responses 为 `ResponsesProvider → electronFetch`。每个文件保留最终 `payload`，并镜像 `messages` / `tools` 便于离线分析。
- 五桶只统计最终 `messages + tools`：过仓里真 tokenizer（`src/host/context/tokenEstimator.ts` → gpt-tokenizer **cl100k_base BPE**）。工具桶严格取每个工具的 `name + description + parameters`。model、stream、store 等协议控制字段不入桶。
- **cl100k 不是"真值"，只是比 ÷3 准一个数量级**：Neo 实际跑的是 DeepSeek / Kimi 这类模型，它们的 tokenizer 不是 cl100k_base。唯一真值是 provider 侧回报的 `inputTokens`，故下表继续与它并列（见下条），不互相替代。分桶归因只能靠本地 tokenizer——provider 只给总数。
- 静态系统提示取首个 system message；后续 system message按来源分为运行时注入与 nudge；其余 user / assistant reasoning / function_call / function_call_output 均归历史消息。
- provider `inputTokens` 来自真实 `model_call` usage。缓存命中轮出现 157 / 107 这类低值，说明它不是完整请求体体积账本，故与本地 tokenizer 估算并列、不互相替代。
- 初版原始 dump 位于 `/tmp/l8-att1-normal.P8vU04`、`/tmp/l8-att1-goal.y7641n`、`/tmp/l8-att1-multi.blX6xJ`，含本机路径与用户输入，不进仓库，**统计后即删**（这正是本次重算必须重跑取证的原因，见下条）。

- **重算的证据来源**：初版四场景的原始 dump 在统计后即删（含本机路径与用户输入），无法回头对同一份文本换尺。N-L8-RECALC 的做法是**在 ATT1 那次提交的代码快照（`b668b7ded`）上原样重跑普通场景**（同模型 `custom-tokenrhythm/deepseek-v4-flash-0731`、同 Responses 协议、同一条「读 package.json」任务、同样 2 轮），拿到新的真实请求体后**先用 ÷3 复算、与初版数字逐项对齐验证方法学**，再换真 tokenizer。对齐结果：工具桶 ÷3 合计 **10987**、逐工具 `TaskManager 2502 / WebSearch 1233 / Grep 855 / Bash 715 / MemoryWrite 745 / Write 567 / Edit 519 / Glob 451 / AskUserQuestion 377 / Read 376` **与初版逐个精确相同**，故工具桶的真值是实测（A 档）。静态提示桶 ÷3 复算 11117 vs 初版 10862（差 2.3%，来自 worktree 路径与 git 状态不同），故该桶及运行时/nudge/历史三桶按**本次实测的分桶比值**换算（B 档，比值与换算过程见 §重算对照）。

### 翻转了的结论（共 3 条）

1. 🔴 **首轮第一大桶从「工具 schema」变成「静态系统提示」**。÷3 口径下普通场景是 45.3% vs 44.8%（schema 险胜）、goal 50.6% vs 48.4%、多 agent 49.6% vs 49.2%——**三个场景全部是 schema 排第一**；换真口径后三个场景全部反转成静态提示第一，且不是险胜：普通 49.1% vs 38.2%、goal 54.1% vs 44.6%、多 agent 55.4% vs 43.0%。**静态系统提示比工具 schema 大 21%～29%。**
2. 🔴 **工具 Top10 的名次换血**：`Bash`/`MemoryWrite` 互换；中文 description 的 `delegate_task`、`recommend_capability` 从第 15 / 17 位升进 Top10，把 `AskUserQuestion`、`Read` 挤出去（明细见上一节）。
3. 🔴 **棘轮门的语音固定开销基线原本与真实成本无关**：÷3 记 60、真值 93，而门的允许区间是 49.5–60.5——**真值落在区间外 55%**，换句话说那道门此前守的是一个不存在的数。已在本单一并修正（见 §固定开销棘轮证据）。

### 没有翻转的（同样要写清楚）

- **语音场景的桶序未变**：÷3 与真口径下都是「静态提示 > 工具 schema > 运行时注入 > 历史」，只是差距从 1.40 倍拉大到 1.93 倍。语音本来就是唯一天然不带 TaskManager 的场景，schema 桶小，所以不靠换尺也排得对。
- **重复候选清单的排序未变**（本单原本预期它会翻转，实测没有）。逐条读了引用的 file:line 后确认：第 1–6 条的正文**全部是英文提示词**（`base/tools.ts` 的 Rules 表、`identity.ts` 的 `<tool_discipline>`、`taskManager.schema.ts` 的 Evidence gate、`contextBuilder.ts` 的 `<env>` 块都是英文），只有第 7 条 `checkpoint-nudge` 是中文。所以 1–6 条统一下调约 28%、第 7 条上调 28%，**名次一个没动**。唯一值得记的变化是第 7 条与第 6 条从 13 vs 28（差 2.2 倍）变成 17 vs 20（几乎持平）——那条「同名标签字节级重复」的性价比比原先看上去高一档。
- **各表的总量方向未变**：真口径总计一律低于 ÷3 总计（普通轮1 20660 vs 24251，−15%），因为占大头的两桶都是被高估的那一类。**注意这不代表"成本变低了"**——真实成本一直是这个数，只是以前算错了。
- **provider `inputTokens` 与本表的关系未变**：仍然只能并列参照、不能互相替代（缓存命中轮的 157 / 107 这类低值依旧存在）。真口径把普通轮1 的差距从 24251 vs 20966（+15.7%）收窄到 20660 vs 20966（−1.5%），**方向反了但绝对偏差从 3285 降到 306**——这是换口径正确性的一个旁证：本地 cl100k 估算比 ÷3 更贴近 provider 实际计费。

### 换算方法与它的边界

工具桶是逐工具实测（A 档）。其余四桶因原始 dump 已删，取本次实测的分桶比值乘上初版 ÷3 值（B 档）。语音的静态提示桶做了两段拆分（基底 9911 走 0.933、SKILL.md 增量走 1.206），因为这两段语言构成差异极大，混在一起用单一比值会错 200 token 以上。

**这套换算的已知误差来源**：① 比值取自普通场景，goal / 多 agent / 语音的桶内语言构成可能略有不同；② 语音工具桶有 22 token（0.3%）口径差未溯源；③ cl100k_base 本身不是 DeepSeek/Kimi 的 tokenizer。**结论级别的判断（谁大谁小、差多少倍）不受这三条影响**——最大的一条误差也只有个位数百分比，而翻转的那几条差距都在 20% 以上。

### 🔴 顺带查出：CORE schema 预算门量的是一段模型看不到的死文本

重算时对账发现，线上 16 个工具的 schema 合计 **4628** token，而 `tests/unit/tools/coreToolSchemaBudget.test.ts` 的基线是 **4349**——差 **279**，全部来自 `WebSearch` 一个工具。

机制本身 ATT6 报告的 §证据与口径 已经记过（「`WebSearch` 855 vs 1233 是 `dynamicDescription()` 运行时拼接」）：`toolDefinitions.ts:64` 的合并序是 `cloud > dynamic > static`，而 `webSearch.schema.ts` 同时写了 `description`（394 字符）和 `dynamicDescription()`（1487 字符），**线上永远发后者，前者一个字都到不了模型**。**新的一条是**：晚于那份报告建起来的 CORE schema 预算门，读的恰恰是 schema 文件里那段到不了模型的 `description`。

后果是双向的：把 `description` 压瘦能让门变绿而线上一分钱不省；把 `dynamicDescription` 写胖门则完全看不见。CORE 里目前只有 `WebSearch` 一个工具有 `dynamicDescription`，所以影响面是 279 token/轮、6.4%。

**本单没有动那道门**（它的 tokenizer 口径本来就是对的，与本单要修的问题不是一回事；改成调用 `dynamicDescription()` 会让门吃进日期字符串等非确定性输入，需要单独设计）。已记为派生单 **N-L8-SCHEMAGATE**。
